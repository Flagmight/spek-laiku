# Registration and Email Verification Research

## Decision

Use ASP.NET Core Identity for user creation, password hashing, normalized email uniqueness, password protection, and email-confirmation tokens. Add a persisted `AccountStatus` value to distinguish pending verification from active and suspended accounts.

The registration flow will create a user in `PendingVerification`, generate an email-confirmation token, send it through an `IEmailSender` abstraction, and leave the user signed in only as a pending session. Protected application operations will require an authenticated, verified account.

## Rationale

- The constitution requires ASP.NET Core Identity for authentication and user management.
- The specification requires case-insensitive duplicate detection, protected passwords, and an account lifecycle state.
- Identity already provides token generation and email-confirmation semantics, avoiding custom password hashing or token cryptography.
- A separate status property is required because `EmailConfirmed` alone does not represent the complete account lifecycle or authorization state.
- Keeping email delivery behind an interface avoids coupling the registration service to a mail provider and allows deterministic test delivery.

## Alternatives Considered

### Custom account verification

Rejected because it duplicates Identity behavior and would introduce custom token storage, hashing, expiry, replay, and invalidation logic.

### Immediate account activation

Rejected because the specification requires email confirmation before protected use and the account must remain in a distinct pending state.

### Email confirmation without account status

Rejected because the application needs to distinguish pending, active, and suspended accounts for authorization and UI behavior.

### Provider-specific email sender in the registration service

Rejected because it would couple business rules to one delivery provider and make tests depend on external infrastructure.

## Email Delivery Choice

A production mail-provider implementation will be selected during implementation and documented in the feature plan. The abstraction contract must support asynchronous delivery, recipient validation, and failure reporting without exposing message content or tokens to logs.

The initial implementation must not rely on live email delivery in tests. Tests will replace the sender with a deterministic fake while exercising the registration and verification service behavior.

## Security Considerations

- Email confirmation links must contain a user ID and token and must be delivered only to the submitted email.
- Tokens must be generated by Identity, never constructed manually.
- Tokens must not be returned in API responses or written to logs.
- Confirmation links must expire through Identity token semantics.
- A successful verification must set both `EmailConfirmed` and `AccountStatus = Active` atomically from the application's perspective.
- A failed or expired verification must leave the account pending and must not grant protected access.
- Duplicate registration attempts must be handled without revealing account existence beyond the requirement already specified.

## Validation Strategy

- Backend unit tests will cover validation, duplicate handling, pending-state creation, verification success, expired or invalid tokens, and authorization denial.
- Backend integration tests will use a fake email sender and an isolated test database.
- Frontend tests will cover registration success, pending verification, validation errors, server errors, and protected-feature access.
- The full backend build and tests plus frontend lint, tests, and build are required before completion.
